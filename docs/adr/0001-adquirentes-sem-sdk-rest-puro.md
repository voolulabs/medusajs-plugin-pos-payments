# ADR 0001 — Adapters de adquirente em REST puro; SDK só quando cobrir a superfície Cloud/terminal

- **Status:** Aceito
- **Data:** 2026-09-25
- **Escopo:** `@voolulabs/medusajs-plugin-pos-payments` Fase 1 (provider manual e integração)
- **Nota de localização:** Canônico neste arquivo (`docs/adr/` do repo do plugin); origem histórica no workspace `adr/`.
  então migra para `medusajs-plugin-pos-payments/docs/adr/0001-…`.

## Contexto

O plugin cobre **4 adquirentes brasileiras** (Mercado Pago, SumUp, Stone/Pagar.me, Cielo) para
**pagamentos presenciais**: o backend comanda a maquininha via
Cloud API e o POS acompanha a confirmação. Getnet, PagBank, Sicoob/Sipag e Rede estão em escopo
separado ([escopo-separado.md](../escopo-separado.md)) e não fazem parte desta decisão. A superfície por adquirente é sempre a mesma: criar ordem
no terminal, consultar status, cancelar, reembolsar, listar terminais, OAuth de onboarding (Fase 2b)
e webhooks.

**Pressupostos do ecossistema (verificados):**

- Providers de pagamento oficiais do Medusa **embarcam o SDK oficial como runtime dependency**
  (`@medusajs/payment-stripe` depende de `stripe` ^15.5.0). Ou seja, "zero deps" **não** é o padrão
  de payment provider do ecossistema — é um **desvio deliberado deste projeto**, que precisa se
  justificar por si (cobertura de superfície, não por convenção).
- Plugins que só adicionam rotas (como o `@narisolutions/medusa-plugin-pos`) costumam ter zero
  runtime deps; esse é o espírito de instalação enxuta que o plugin herda.

**Cobertura real dos SDKs oficiais para a nossa superfície (verificada no código-fonte — repos
e tarballs npm, 2026-09-26):**

- `mercadopago` (Node 3.6.1, repo `sdk-nodejs`): o client `order` cobre o ciclo completo da
  **Orders API v1**
  (`create/get/cancel/capture/process/refund/search/transaction` em `src/clients/order/*`), os
  tipos documentam `type: "point"`, `external_reference`, `expiration_time`,
  `config.payment_method` (`default_installments`, `installments_cost`) e `requestOptions`
  aceita idempotency key. **O que falta para o nosso fluxo (verificado no código):** o tipo
  `Config` **não tem a chave `point`** (o direcionamento ao terminal `config.point.terminal_id`
  — campo crítico do Point — exige type-escape); **não há** listagem de terminais
  (`GET /terminals/v1/list`), `PATCH /terminals/v1/setup` nem simulação (`POST /v1/orders/{id}/events`);
  e o client `point` do SDK é a superfície **legada** Payment Intents (`/point/integrations/…`,
  descontinuada na prática pela migração oficial para Orders).
- `sumup-ts` → **`@sumup/sdk` 0.2.0**: o repo `sumup/sumup-ts` foi adotado pela SumUp e publicado
  sob escopo oficial; o código é **gerado pelo codegen da SumUp a partir da OpenAPI oficial**
  (`// Code generated by @sumup/sumup-ts-codegen. DO NOT EDIT.`) e o recurso `readers` cobre a
  superfície completa (list/create por pairing code/go-checkout/checkout/get/terminate/status);
  ativo (push 2026-09); é o SDK que o **plugin oficial SumUp↔Medusa** usa.
  Pré-v1 do SDK (breaking changes possíveis) → pin + reavaliação por minor.
- Pagar.me/Stone: `@pagarme/pagarme-nodejs-sdk` (v7.0.2, APIMATIC-generated): o modelo
  `CreateOrderRequest` **não contém `poi_payment_settings`** (nem qualquer campo Connect) e carrega
  **schema de validação embutido** (`createOrderRequestSchema`) que
  rejeita/descarta campos fora do contrato; além disso tipa `payments: CreatePaymentRequest[]` e
  `code` como **obrigatórios** — enquanto o fluxo Connect Direto cria o pedido **sem** `payments`
  (o pagamento acontece no terminal via `poi_payment_settings`). Ou seja: **não é apenas
  cobertura incompleta — o SDK está em conflito com o fluxo que o adapter usa.** A superfície do
  Connect 2.0 tem portal próprio (connect-stone.stone.com.br, corpus de 43 páginas varrido) e é
  outra API.
- Cielo: não há SDK oficial; os pacotes community (ex. `cielo`) implementam a API e-commerce 3.0 —
  a Conecta é outra API, documentada no portal próprio (docs.cielo.com.br/conecta, páginas `.md`
  via `llms.txt`; spec OpenAPI embutida na página de Baixa de Parâmetros — não há spec única da
  superfície transacional).
**Riscos de dependência de SDK:** peso e CVEs de terceiros; breaking changes (agravado no pré-v1);
camada entre o teste do adapter e a API real que envelhece; e o agravante específico do mercado:
**a superfície presencial muda rápido** — o Mercado Pago migrou de Payment Intents para a Orders API
`/v1/orders` recentemente, e SDKs costumam lagar essa migração.

**Requisitos funcionais que qualquer via precisa cumprir** (descobertos na revisão adversarial):
idempotência obrigatória nas operações monetárias (`X-Idempotency-Key` é **exigido** pelo MP em
criação/cancelamento/reembolso — UUID v4 sugerido; chave reutilizada com body diferente em 24 h retorna
`idempotency_key_already_used`), unidades monetárias divergentes entre adquirentes, e webhooks que
não podem ser fonte de verdade.

## Opções consideradas

1. **SDK oficial em todo adapter** — rejeitada: para a maioria das adquirentes o SDK não cobre (ou
   não documenta cobrir) a superfície de terminal; adicionaria dependências inúteis e uma camada
   não testada entre o adapter e a API.
2. **REST puro (`fetch`) em todos os adapters** — o padrão escolhido, mas purismo cego rejeitaria
   um SDK que de fato cobre nossa superfície (SumUp).
3. **REST puro por padrão + exceção criteriosa por adapter** — **escolhida**.
   Contra-argumentos a favor de SDK, respondidos: *tipos oficiais de graça* — a fronteira do
   adapter é validada por zod de qualquer forma; os tipos do SDK duplicam a
   camada. *Menos drift quando o adquirente muda* — o mercado mostra o oposto: o MP migrou
   Payment Intents → Orders e o client `point` do próprio SDK ficou preso no legado. *SDK
   parcialmente (orders no SDK, terminais em REST)* — rejeitada: dois estilos de HTTP/erro/retry
   no mesmo adapter, idempotência e token cache em dois lugares, sem cobrir os endpoints que
   faltam.
4. **Sub-opção aprovada da via REST**: tipos gerados em **build-time** a partir de OpenAPI oficial
   da adquirente (zero runtime dep). Válida quando existir spec confiável (SumUp publica — o SDK
   oficial é exatamente isso; **MP publica o repo oficial `mercadopago/openapi`** com
   `by-product/{orders,pos,chargebacks,oauth}/spec3.yaml` — confirmado 2026-09-26; Cielo publica
   OpenAPI embutido só na página de Baixa de Parâmetros, sem spec única da superfície
   transacional).

## Decisão

1. **Padrão: adapters falam REST direto via `fetch`**, sem dependências de SDK. Cada adapter é o
   único lugar que conhece o contrato HTTP da adquirente, e declara em comentário-cabeçalho qual
   contrato/versão usa (ex.: "MP Orders API, pós-migração payment-intents, 2026-09").
2. **Exceção por adapter**, aceita somente se todas as condições forem verdadeiras:
   - o SDK cobre **e documenta** a superfície Cloud/terminal que o adapter usa;
   - import **lazy** dentro do adapter (adquirente não configurada não paga o custo);
   - **versão pinada**, com política de reavaliação periódica (pré-v1 exige revisão a cada minor);
   - testes do adapter rodam contra sandbox/simulador da adquirente;
   - ADR específico do adapter registra a justificativa.
3. **Primeira exceção aceita: SumUp** — **`@sumup/sdk`** (escopo oficial do repo `sumup/sumup-ts`),
   **gerado por codegen da própria SumUp a partir da OpenAPI oficial**, com cobertura completa da
   superfície de readers e adotado pela SumUp no seu plugin oficial Medusa. Entra na Fase 3.
4. **Mercado Pago (piloto, Fase 2): REST puro.** O SDK 3.6.1 cobre a maior parte da Orders API v1
   (ciclo completo + idempotência + `type: "point"` documentado), **mas não tipa
   `config.point.terminal_id`** — o campo crítico de direcionamento ao terminal, que exigiria
   type-escape —, **não tem** terminais (list/setup) nem simulação, e seu client `point` é a
   superfície **legada** Payment Intents. O adapter usa terminais e simulação de qualquer forma;
   dividir o fluxo entre SDK (orders) e REST (terminais/simulação) criaria dois estilos de
   HTTP/erro/retry sem cobrir o que falta — o helper HTTP comum dá idempotência/retry/token/cache/
   logging uniformes (regra §2 segue valendo para reavaliação).
5. **Stone (Fase 3): REST puro — SDK descartado para o fluxo Connect.** O modelo de criação do
   SDK **não aceita `poi_payment_settings`** e o schema embutido + campos obrigatórios
   (`payments[]`, `code`) conflitam com o fluxo Direto (pedido sem `payments`). O SDK v7 poderia
   servir rotas genéricas da v5, mas não justifica a dependência
   (portal Connect — corpus de 43 páginas).
5a. **OAuth de onboarding (Fase 2b) não requer SDK** — redirect + troca de código (e refresh token)
    são HTTP puro nas adquirentes com OAuth.
6. **Requisitos obrigatórios de qualquer adapter** (independem da via):
   - **Idempotência**: toda operação monetária usa chave de idempotência estável por operação
     (derivada do pagamento/sessão no Medusa), persistida antes do primeiro envio; retry reutiliza a
     MESMA chave; `idempotency_key_already_used` é tratado re-consultando o recurso, nunca recriando.
   - **Unidades monetárias**: cada adapter documenta em um único lugar a unidade da adquirente
     (decimal string vs minor units) e a conversão a partir dos minor units do Medusa — bug clássico
     de dinheiro, teste obrigatório.
   - **Webhooks são pistas, não verdade**: estado autoritativo sempre re-consultado na API da
     adquirente antes de capturar/marcar pago; verificação de assinatura (onde existir — ex. HMAC da
     SumUp) é camada adicional, nunca substituta do re-fetch.
   - **Falhar fechado em dinheiro** (padrão dos providers consolidados — easypayment/paypal,
     lambda-curry/braintree): `authorizePayment`/`capturePayment` só retornam sucesso com o estado
     comprovado na adquirente — resposta 2xx **não** é dinheiro (re-consultar status; pendência de
     terminal/PAYER_ACTION fica `pending`/`REQUIRES_MORE`, nunca "autorizado"); acquirer reference
     armazenado só é considerado válido com status comprovado (COMPLETED/successful).
   - **Montante dentro da chave de idempotência** para capture/refund
     (`capture-{ref}-{amount}`): adquirentes deduplicam pela chave, e dois parciais sequenciais
     com a mesma chave colidiriam (padrão easypayment/paypal).
   - **Webhook handler**: tópicos/refs estranhos → `not_supported` (2xx, sem retry storm);
     falhas transientes propagam para o core retriar; assinatura comparada com
     `crypto.timingSafeEqual` (ecossistema usa `!==` — gorga/paystack); **secret ausente = erro de
     boot**, nunca "pular verificação silenciosamente" (anti-padrão do gorga).
   - **Dinheiro nunca em float**: conversões via `MathBN` (`@medusajs/framework/utils`) —
     `19.99 * 100 === 1998.999…` (bug documentado no paystack); função única por direção com
     teste do caso de drift.
   - **Rate limits**: helper HTTP comum respeita 429 + `Retry-After`.
7. **Fora de escopo explícito** (não disparam esta decisão): SDKs mobile/nativos (TEF, Bluetooth/
   PlugPag, SmartPOS, LIO) e bibliotecas de checkout online/criptografia de navegador.

**Evidência de cada linha (onde foi verificado, 2026-09-26):**

- MP: código do SDK em github.com/mercadopago/sdk-nodejs (`src/clients/order/*`, `src/clients/order/create/types.ts`, `src/clients/order/commonTypes.ts` — `Config` sem chave `point`).
- SumUp: código gerado em github.com/sumup/sumup-ts (`sdk/src/resources/readers/index.ts`, cabeçalho codegen) + uso no plugin oficial `sumup/sumup-plugin-medusa`.
- Stone: tarball npm `@pagarme/pagarme-nodejs-sdk@7.0.2` (`dist/cjs/types/models/createOrderRequest.d.ts` — sem `poi_payment_settings`, schema APIMATIC).
- Cielo: ausência confirmada por busca (registries + docs.cielo.com.br); community = e-commerce 3.0.
- Contrato das superfícies: especificações verificadas por adquirente na pesquisa interna (MP Point, SumUp, Stone Connect, Cielo Conecta).

## Consequências

**Gatilho de reavaliação:** release relevante de qualquer SDK desta tabela (`mercadopago` com
terminais/ponto tipado, `@sumup/sdk` minor/major, `pagarme` v8) reabre a exceção §2 para o
adapter.

**Positivas**
- Instalação enxuta e previsível; adquirente sem credenciais custa zero.
- O teste do adapter exercita o mesmo caminho de produção (sem camada de SDK no meio).
- Menor superfície de supply chain; breaking changes de terceiros não chegam via upgrade transitivo.
- Obrigações críticas (idempotência, unidades, re-fetch de webhook) ficam **explícitas no código do
  plugin** em vez de implícitas num SDK — com teste para cada uma.

**Negativas / custos aceitos**
- Clients HTTP à mão por adapter (payloads, erros, retries) — o custo real do plano; mitiga-se com o
  helper HTTP comum do plugin.
- Tipagem declarada localmente ou gerada em build-time a partir de OpenAPI (quando existir).
- Pré-v1 pinado (SumUp) exige revisão manual de versões.
- Churn de API presencial (caso MP) afeta o adapter diretamente — com SDK também afetaria, via
  lag de versão; o comentário de contrato + E2E por adapter é a mitigação escolhida.

**Riscos residuais registrados**
- Adquirente sem simulador de terminal em sandbox: teste do fluxo completo exige hardware físico
  (risco por adapter, independente da via SDK/REST) — avaliar por adapter na Fase 3.
- **Stone não oferece sandbox** (confirmado nos docs oficiais): validação direto **em produção** com
  valores mínimos e estorno imediato pelo terminal; **estorno sem rota de API** (POS/Portal Stone) —
  o `refundPayment` do adapter Stone documenta o procedimento ao operador em vez de chamá-lo.

## Compliance (checklist para novos adapters)

1. Superfície coberta/documented por SDK oficial? Se sim: justificar REST **ou** aplicar a exceção
   (lazy + pin + reavaliação periódica + ADR do adapter).
2. Idempotência com chave estável por operação, persistida antes do envio; retry reutiliza a chave.
3. Unidade monetária da adquirente documentada e convertida em um único lugar; testada.
4. Webhook nunca é fonte de verdade; estado re-consultado na API antes de capturar.
5. Contrato/versão da API declarado no cabeçalho do adapter; E2E contra sandbox/simulador.
6. Nenhuma dependência nova no `dependencies` do pacote sem ADR que a justifique.
